# Research assumptions and limits

1. No `Docs Thesis 1 - Group 4.pdf` was available. The supplied master prompt is the Phase 1 specification. Chapter 3 hardware, data-flow, operating, and test procedures need reconciliation when the document becomes available.
2. The hardware chain remains PZEM-004T V3.0, ESP32, Raspberry Pi 4, Wi-Fi, Python backend, and PostgreSQL. MG996R breaker actuation remains a proposal requiring separately reviewed electrical safety design and adviser approval.
3. Three demonstration units each have one meter, one prepaid account, and one tenant. More units can be registered. Shared meters, tenant turnover, and multi-tenant accounting require an explicit policy; the prototype creates accounts only in currently unassigned units.
4. All seeded and simulator readings are synthetic. Their stored source and UI labels distinguish them from separately registered hardware devices. Data and account history are not automatically converted when disabling simulation.
5. No payment gateway or automatic payment verification exists. An administrator approves prototype credit manually. Approval is not evidence of receipt of real money.
6. Stored financial arithmetic uses PHP with six decimal places for usage deductions and two places for load requests. This avoids rounding each five-second update to zero cents. Utility billing rounding and settlement rules need adviser review.
7. Interval consumption crossing rate boundaries is prorated by elapsed time. There is insufficient information to recover the exact within-interval load curve. More frequent meter readings reduce that uncertainty. Rate changes cannot be backdated through the UI.
8. The first meter reading and confirmed reset are zero-cost baselines. Reset-gap usage cannot be reconstructed reliably. Communication gaps with continuous cumulative counters are billed on ordered recovery; simulator shutdown gaps are explicitly logged and not fabricated.
9. Hardware balances can become negative after measured overrun. Exhaustion logs a review-required condition; observed electrical state remains unchanged until hardware reports a change. This is not an approved disconnection policy. Simulated exhaustion and restoration are software demonstrations only, and protective trips never automatically reclose.
10. Device connectivity requires both a recent arrival (30 seconds) and a recent measured sample (90 seconds). Raspberry Pi presence is inferred only from authenticated communication. This is not a direct operating-system health or Wi-Fi signal measurement.
11. Forecasting remains Phase 4. Synthetic seven-day data do not establish real-device forecasting accuracy. The UI deliberately reports insufficient historical data and no remaining-credit-duration estimate.
12. Physical PZEM accuracy, continuous endurance, Wi-Fi recovery, response/acknowledgment timing, calibration, and prepaid expiration criteria require actual experimental procedures. There are no fabricated research results.
